# Security Policy

## Reporting a vulnerability

**Do not open a public issue for a security problem.**

Report it privately through
[GitHub Security Advisories](https://github.com/Life-Experimentalist/RanobeGemini/security/advisories/new),
or by email to <github@vkrishna04.me> with `SECURITY` in the subject.

Please include what you can of:

- the version, from the extension's popup or `manifest.json`
- the browser and its version
- the site the extension was running on, if the issue is page-dependent
- steps to reproduce, or a proof of concept
- what an attacker gets out of it

You should get an acknowledgement within 72 hours and an assessment within
seven days. If a fix is warranted it goes out in the next release, and you get
credit in the release notes unless you'd rather not.

This is a spare-time project, not a funded one — there is no bug bounty, and
response times are best-effort rather than contractual.

## Supported versions

Only the latest released version receives security fixes. Browser add-on stores
auto-update by default, so in practice this is what nearly everyone is running.

| Version | Supported |
|---|---|
| 5.x | Yes |
| 4.x and earlier | No |

## What this extension is responsible for

The extension is local-first: your data does not pass through any server of
ours, so there is no service of ours to breach it out of. That shifts the
interesting attack surface into the browser, and specifically to these things:

**Credentials.** API keys and OAuth tokens live in `browser.storage.local`,
unencrypted, which is the same protection the browser gives its own saved
passwords at rest. Anything with filesystem access to the browser profile can
read them. This is a known and accepted property of extension storage, not a
defect we can fix from inside the extension — but a bug that *leaks* those
values somewhere they should not go (into a page, a log, a network request to
the wrong origin, a backup file) is very much in scope.

**Injected content.** The extension writes AI-generated text into pages it does
not control. A path where that text can execute as script, or where page-
controlled content can reach a privileged extension context, is in scope.

**Message passing.** The background worker accepts messages from content
scripts and extension pages. A path where an arbitrary web page can reach a
privileged handler is in scope.

**Cloud sync.** Backups to Google Drive, OneDrive, Dropbox, or WebDAV are
optional and off by default. A bug that sends data to the wrong destination,
that includes credentials in a backup, or that grants broader OAuth scope than
the feature needs, is in scope.

## What is out of scope

- The security of the AI provider or cloud storage service you chose. Their
  handling of your data is governed by their terms, not ours.
- Content extracted from novel sites being wrong or incomplete. That is a bug,
  but not a security bug — please file it as a normal issue.
- Anything that requires an attacker to already have code execution or
  filesystem access on the user's machine.
- Reports generated by an automated scanner with no demonstrated impact.

## What the extension sends where

Useful context when judging whether something is a leak:

| Data | Leaves the browser? |
|---|---|
| Chapter text | Only to the AI provider you configured, with your key |
| Your library and reading history | Only to the cloud backup you configured, if you enabled one |
| API keys and OAuth tokens | Never — only to the service that issued them, as authentication |
| Anonymous usage counts | Only if you turn telemetry on; it is off by default |

Nothing routes through a server of ours. The one first-party endpoint that
exists at all is the telemetry collector, which is contacted only after you
switch telemetry on, and only with counts.

So: if you observe the extension contacting a host that is not one of your
configured AI or sync providers, not one of the supported novel sites, and not
the telemetry endpoint you opted into — that is a finding. Please report it.
