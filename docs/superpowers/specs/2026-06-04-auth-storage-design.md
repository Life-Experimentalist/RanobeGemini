# Auth-for-Storage Solutions — Design Spec

**Date:** 2026-06-04  
**Status:** Approved for implementation

---

## Context

The storage sync system (`src/background/storage/`) already implements a modular adapter pattern with four providers: Google Drive, Dropbox, OneDrive, and WebDAV. Each uses `browser.identity.launchWebAuthFlow` via `src/utils/oauth-pkce.js` for OAuth2 PKCE flows.

**The gap:** `browser.identity.launchWebAuthFlow` is unreliable on mobile browsers (Edge Android, Firefox Android) and unavailable in some Chromium builds. When it fails, authentication silently breaks with no fallback. The landing page at `landing/oauth-redirect.html` already handles the OAuth callback with `window.opener?.postMessage()`, but this only works when the page is opened as a popup (desktop). On mobile, tabs are opened without a window opener, so the `postMessage` silently goes nowhere and auth hangs.

---

## What to Build

### 1. Landing page: add `chrome.runtime.sendMessage` fallback

**File:** `landing/oauth-redirect.html`

When `window.opener` is null (mobile tab case), parse the OAuth response from the URL and use `chrome.runtime.sendMessage` to pass the token back to the extension. The extension ID must come from the URL `?ext_id=` parameter (already passed via the `launchOAuthTabFlow`).

The page already tries `window.opener?.postMessage()` — add the `sendMessage` branch as the else path:

```
if window.opener → postMessage (existing, works on desktop)
else if ext_id in URL and chrome.runtime.sendMessage available → sendMessage
else → show "Login successful, you may close this tab" (user closes manually)
```

### 2. Background: handle incoming auth tokens from landing page

**File:** `src/background/background.js`

The existing `onMessageExternal` listener handles only `EXTERNAL_PING`. Extend it to also handle the OAuth token relay:

- Message shape from landing page: `{ source: "ranobe-gemini-oauth", accessToken?, authorizationCode?, state?, expiresAt? }`
- On receipt: store the payload in a short-lived in-memory promise resolver keyed by `state`
- This lets `launchOAuthTabFlow` (below) await the result with a timeout

The state nonce is generated by `launchOAuthTabFlow` before opening the tab, so it can match the incoming message.

### 3. `oauth-pkce.js`: add `launchOAuthTabFlow` function

**File:** `src/utils/oauth-pkce.js`

New exported function that replaces `launchWebAuthFlow` with a tab-based flow:

```javascript
export async function launchOAuthTabFlow({ authEndpoint, clientId, redirectUri, scope, challenge, extra = {}, timeoutMs = 120_000 })
```

Steps:
1. Generate a `state` nonce (already done in `launchOAuthPkceFlow`)
2. Build auth URL with `ext_id=browser.runtime.id` appended to redirect URI params (so the landing page knows where to `sendMessage`)
3. Open a new tab via `browser.tabs.create({ url: authUrl })`
4. Register a one-shot promise resolver in a shared `pendingAuthFlows` Map keyed by `state`
5. Wait up to `timeoutMs` for the background message handler to resolve it
6. Clean up the tab on success or timeout
7. Return the auth code (same output shape as `launchOAuthPkceFlow`)

### 4. Update each provider util to try tab flow on `launchWebAuthFlow` failure

**Files:** `src/utils/drive.js`, `src/utils/dropbox.js`, `src/utils/onedrive.js`

Wrap the existing `browser.identity.launchWebAuthFlow` call in a try/catch. If it throws (or if `browser.identity` is unavailable), call `launchOAuthTabFlow` with the same parameters:

```javascript
try {
    code = await launchOAuthPkceFlow({ ... });  // uses launchWebAuthFlow
} catch (_err) {
    code = await launchOAuthTabFlow({ ... });   // tab-based fallback
}
```

This is a non-breaking change — desktop flows continue to use the fast `launchWebAuthFlow` path.

## Data Flow (Mobile Tab Case)

```
Extension background
  → browser.tabs.create(authUrl + ext_id param)
      ↓
OAuth provider (Google/Dropbox/OneDrive)
  → redirects to: landing/oauth-redirect.html?code=XYZ&state=ABC&ext_id=<id>
      ↓
oauth-redirect.html script
  → window.opener is null (mobile tab, no opener)
  → chrome.runtime.sendMessage(ext_id, { source: "ranobe-gemini-oauth", authorizationCode, state })
      ↓
background.js onMessageExternal
  → finds pending resolver by state
  → resolves the launchOAuthTabFlow promise
      ↓
launchOAuthTabFlow returns auth code
  → exchangeCodeForTokens(code) → stores access + refresh tokens
```

## Out of Scope

- Changing the existing adapter interface (the `uploadBackup`/`listBackups` contract stays as-is)
- Adding new providers (OneDrive is already implemented)
- UI changes — provider selection UI already exists in Library Settings
- The `chrome.runtime.sendMessage` approach requires `externally_connectable` in manifests listing the landing page URL — verify this is present before implementing
